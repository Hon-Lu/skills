# 建議規則：審別人的 MR

建議有四種：阻擋、建議、待查證、不提。留言會花作者的時間，門檻比審自己的分支高。等級不列入判斷。REVIEW.md 的建議摘要寫成 `阻擋 1；建議 2、3；待查證 4；不提 5、6`。

## 阻擋

你親自查證成立、這個 MR 造成，而且合併後會寫壞資料、造成安全回歸或讓主要流程故障。

## 建議

你親自查證成立、這個 MR 造成，而且講得出不改的具體後果，值得作者評估。

## 待查證

風險具體，但只有作者或外部環境才能確認。寫明要確認什麼、該問誰。repo 與本機唯讀資源查得到的先查完，作者只處理你查不到的部分。

## 不提

建議欄寫成 `不提：<理由>`，並附上證據。

| 理由 | 成立條件 |
| --- | --- |
| 需求已定案 | ticket、規格或 issue 明訂這樣做，或明訂這次不做 |
| 條件不成立 | 順著程式碼或環境查過，觸發條件走不到 |
| 不是這次造成 | diff 沒有動到這段 |
| 非專案規範 | 依據只有審查者或使用者的個人設定，或只是風格偏好 |
| 純屬推測 | 這次沒有回歸，提出來只是要作者回頭證明自己沒漏 |
| 影響輕微 | 查證成立，但後果輕到不值得佔用作者的時間 |

判不準風險是否存在時，歸待查證。

## MR-COMMENT.md

把阻擋、建議、待查證的條目寫到 `<run_dir>/MR-COMMENT.md`，依這個順序編號。沒有這三種條目時，只留標題與摘要。

```markdown
## Code Review 結果

- 需阻擋合併：{n}
- 建議調整：{n}
- 待查證：{n}

### 1. [P2] {問題}

{問題與影響}。例如：{觸發情境}。

修改方向：{怎麼改}

驗證方式：{實際怎麼確認的，例如讀過 `file:line`，或用什麼方式實測}
```

這份是給作者看的技術紀錄：直接陳述問題、影響與修改方向，從標題直接進入內容。驗證方式照實寫，待查證的條目把這一行換成「待確認：{要確認什麼}」。

這份只交給使用者，由使用者自己貼到 MR。

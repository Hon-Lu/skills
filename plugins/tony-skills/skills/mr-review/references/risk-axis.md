# Risk 軸：資安、信任邊界與資料一致性

回答一個問題：**本次 diff 是否讓人能做不該做的事、看到不該看的資料，或讓資料在失敗與同時操作下變得不一致？**寫法是否合規屬於 Standards 軸，需求做得對不對屬於 Spec 軸，本軸都不判斷。

本軸的問題幾乎都無法只看 diff 判斷，**每條候選都要實際追查**：從入口（controller、endpoint、handler、job）一路追到資料寫入，確認授權在哪裡檢查、傳入值在哪裡被採用、交易邊界在哪裡開始與結束。

逐節核對本次 diff，**只套用 diff 實際涵蓋的節**；每一節都要在涵蓋清單交代結論。各表的嚴重度是建議值，最終由主流程判定。第 1 至 4 節與技術無關，第 5 節為技術別補充，只在專案使用該技術時適用。

---

## 0. 依據

主流程提供的 repo 規範中，若有授權方式、資料歸屬、交易或鎖定的既有機制（例如統一的授權 attribute、base controller、unit of work、併發控制欄位），先確認本次 diff 是否沿用；**判斷「未被保護」時，以這些既有機制是否實際生效為準**。

本軸是底線：repo 的寫法慣例不會讓本軸的問題失效。

## 1. 資安與權限

| 檢查 | OWASP | 嚴重度 |
| --- | --- | --- |
| 查詢語句由字串拼接使用者輸入組成，未使用參數化查詢 | A03 Injection | P0 |
| Token、密碼、PII 等敏感資料寫入 log 或出現在 response | A02 Crypto | P0 |
| 新增的 endpoint 缺少授權檢查 | A01 Access Control | P0 |
| 使用者傳入的 ID 未做資源擁有權驗證 | A01 Access Control | P1 |
| 角色或操作權限只在前端判斷，後端未檢查 | A01 Access Control | P1 |
| 列表、匯出或查詢未依使用者身分限縮資料範圍 | A01 Access Control | P1 |
| 請求直接繫結至領域模型，未經 DTO 或欄位白名單過濾 | A08 Mass Assignment | P2 |
| 系統邊界缺少輸入驗證 | A03 Injection | P2 |

新增或修改入口時，對照同模組既有入口的授權方式：既有入口都有、本次新增的沒有，是最常見的漏洞形式。

## 2. 後端信任邊界

request、route、query、form、hidden field 與 DTO 傳入的值都由使用者控制。下列資料若直接採用，列為候選：

- 識別資料：資料 ID、所屬單位、使用者 ID。
- 狀態與層級：單據狀態、審核層級、角色。
- 數量與金額：數量、單價、折扣、總額。
- 權限相關值：是否可編輯、是否為管理者等旗標。

可由後端查詢或推導時，應以後端權威資料驗證、正規化並處理。候選要指出是哪個欄位、在哪一行被採用，以及竄改後的具體結果（例如「把 `unitPrice` 改成 0 後，訂單以 0 元成立」）。

## 3. 資料一致性與交易

| 檢查 | 嚴重度 |
| --- | --- |
| Schema 異動缺少對應的 migration 或版本控管腳本 | P1 |
| 多步驟寫入缺少交易包裹 | P1 |

**交易風險細則：**

| 情境 | 嚴重度 | 說明 |
| --- | --- | --- |
| 多次獨立寫入未包在同一交易內 | P1 | 部分成功即資料不一致 |
| 寫入成功後呼叫外部 API 或發送訊息，但無補償機制 | P1 | 外部副作用不可回滾 |
| 單次寫入，但方法名稱暗示多步驟操作（例如 `CreateOrderAndSendNotification`） | P2 | 確認是否需要 outbox 或 saga |
| 交易隔離等級為 read uncommitted | P2 | Dirty read 風險 |

確認實際的交易邊界與 unit of work 範圍，而不是只看方法名稱：寫入是否共用同一個連線或 context、例外發生時哪些寫入已經提交、`catch` 是否吞掉例外讓外層以為成功。

## 4. 併發

| 情境 | 嚴重度 | 說明 |
| --- | --- | --- |
| 讀取後寫入，缺少樂觀鎖（版本或時間戳欄位） | P2 | Lost update |
| 先檢查再建立，缺少唯一約束或冪等保護 | P2 | 重複建立、重複送出 |
| 先讀取餘額或庫存再扣減，未使用條件式更新或鎖定 | P1 | 超扣、負庫存 |
| 狀態轉換未檢查目前狀態仍是預期值 | P2 | 舊狀態覆蓋、重複審核 |

檢查合理的多請求、多使用者或多分頁操作：重複點擊送出、兩人同時編輯同一筆、背景作業與使用者操作同時進行。

候選必須寫出**具體的競爭流程**（例如「兩個請求同時讀到庫存 1，各自扣 1 後寫回，庫存變成 -1」）與**缺少的保護機制**（唯一約束、樂觀鎖、條件式更新、鎖定或冪等鍵）。寫不出競爭流程的，不構成候選。

## 5. 技術別補充

### .NET / C#

只在專案為 .NET / C# 時適用。

| 通用規則 | .NET / EF Core / Dapper 的具體形式 |
| --- | --- |
| 參數化查詢（第 1 節） | Dapper 必須使用參數，不得字串拼接進原始 SQL；EF Core 的 `FromSqlRaw`、`ExecuteSqlRaw` 同樣要使用參數 |
| 授權檢查（第 1 節） | 新 action 缺少 `[Authorize]` 或同 controller 慣用的授權 attribute；controller 層的 `[AllowAnonymous]` 擴大到新 action |
| DTO 或白名單過濾（第 1 節） | 使用 `[Bind]` 或獨立 DTO，不直接繫結 Domain Entity |
| 多次獨立寫入未包在同一交易內（第 3 節） | 多個 `DbContext.SaveChanges()` 未以 `TransactionScope` 或 `BeginTransaction` 包裹 |
| 交易邊界（第 3 節） | 不同 `DbContext` 實例或不同 DI scope 之間的寫入不在同一交易內；Dapper 與 EF Core 混用時未共用同一連線與交易 |
| 樂觀鎖（第 4 節） | 缺少 `RowVersion`、`[Timestamp]` 或 `[ConcurrencyCheck]`，或有欄位但未處理 `DbUpdateConcurrencyException` |
| 條件式更新（第 4 節） | 先查詢實體、在記憶體扣減再 `SaveChanges`，而不是 `ExecuteUpdate` 或帶條件的 `UPDATE ... WHERE` |

# 輸出格式

## REVIEW.md

同一檔分兩區；已確認按 P0–P3 排序，待判斷按條件成立時的影響排序。保留有價值的具體疑點，不設 findings 數量上限。避免多條重複根因掩蓋不同問題。

每條可以獨立貼至 MR；待判斷文字明確使用條件語氣，不能讓讀者誤認已重現。

```markdown
# MR Review

## 已確認問題

### F1 [P1] 具體問題標題

- 類型／變更關聯：回歸；暴露既有缺陷
- 位置：修改位置，及必要的未修改呼叫端位置
- 觸發與影響：操作、前後行為差異、實際資料與回應結果
- 保護查證：已查過的交易／授權／約束／框架機制及為何未擋住
- 修正方向：能修正行為的最小方向

## 待開發者判斷

### R1 [條件成立時 P2] 具體風險標題

- 類型／變更關聯：直接相關的既有風險／尚待查證的回歸
- 已確認事實與位置：具體程式碼事實
- 觸發與可能影響：條件成立時會發生什麼
- 未知條件：逐項列出，不限一項；不得把假設當事實
- 已查保護：哪些確認過，哪些不可見
- 快速驗證／決策：開發者如何確認或選擇接受，不能僅寫「建議確認」
- 修正方向：必要時列可採取的小範圍調整
```

「位置」優先給可供 MR comment 使用的修改行，也提供根因／受影響呼叫端位置；只有未修改位置時說明與本次改動的因果關聯，不為了行號限制丟棄候選。

某區無項目時寫「無」。兩區皆無時仍更新檔案；有查核缺口則明確寫「尚有未查明項，詳見 REVIEW-COVERAGE.md」，不可宣稱完整通過。

不加入稱讚、一般最佳實務清單或不具體的嚇阻文字。純排版、喜好、無關重構、沒有具體路徑的災難猜測不列。

## REVIEW-COVERAGE.md

這是開發者核對「查過什麼／為何沒報」的紀錄，不是另一份 findings。

1. **快照**：模式、target／HEAD／merge-base、commit 範圍、工作區是否另有未提交變更、背景來源、測試範圍。
2. **三軸摘要**：各軸候選數、分流去向、合併指向、是否使用獨立子代理。
3. **影響清單與呼叫鏈表**：使用 trace-and-evidence 格式，列呼叫點總數、已查／未查數。共享行為改動時逐項記錄，不要求對無關程式碼做全站清單。
4. **例外與結果表**：記錄適用的各階段或不適用理由。
5. **逐軸涵蓋**：適用／不適用及位置證據。
6. **候選去向表**：

| 候選 ID | 軸／位置 | 去向／報告 ID | 證據或排除理由 |
| --- | --- | --- | --- |

7. **未查明項**：位置、尚缺資訊、已嘗試的檢查及下一個能釐清的動作；無則明示無。
8. **實際驗證**：執行的命令、成功／失敗／略過、環境限制。說明測試是否觸及本次風險，不把「既有測試通過」當成所有情境已驗證。

只有敏感資料需要遮蔽；不要因輸出只想保留確定問題，就省略待判斷候選或涵蓋缺口。可以精簡文字，但保留足以供另一位開發者複核的證據位置。

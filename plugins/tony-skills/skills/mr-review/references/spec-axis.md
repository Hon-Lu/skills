# Spec 軸：需求符合度

回答一個問題：**本次變更是否正確、完整地實現背景要求，並保留未要求改變的既有行為？**泛用風險由其他軸主查，但發現跨軸疑點時仍交回候選，不能因文件沒寫就丟棄。

需求違反引用原文或驗收條件；既有行為回歸引用 baseline 程式路徑與觀察到的前後差異。文件缺少成功／失敗政策時，提出具體的待判斷風險與需要開發者決定的行為，不編造需求，也不因缺引用刪掉具體程式問題。

---

## 0. 依據

主流程提供的 Spec 依據就是全部的需求來源：

- **模式 A**：使用者提供的 Issue、文件或口頭說明的變更目的。
- **模式 B**：分支對應目錄下的 `spec.md`、`engineering-spec.md`、`issue-doc.md`、`issue.md`，以及 `issues/` 下的 ticket；文件優先序依主流程。

依據沒有提到的行為，以既有行為為準：本軸判斷「有沒有改壞既有行為」，而不是把依據沒寫的推測成新需求。

## 1. 需求缺漏

依據明確要求、diff 中卻缺少或只做了一部分的行為。

- 模式 B 逐張 ticket、逐條驗收條件對照 diff；`engineering-spec.md` 或 `issue-doc.md` 有驗證條件（`VC-xx`）時逐條對照。
- 只做了 happy path、缺少依據明列的錯誤情境、錯誤訊息或邊界值，也屬於缺漏。
- 修正失敗路徑時，一併核對成功流程是否受共用副作用改變影響；修正成功流程時，檢查中途／提交後失敗的回應與資料狀態。
- 依據有要求、但實作刻意延到後續 ticket 的（ticket 相依或範圍已註明），不構成候選。

## 2. 實作與需求不符

看起來做了，但行為和依據不一致。優先核對依據中**可判斷真偽**的描述：

- 條件與邊界值：上下限、是否含等號、日期與時區。
- 狀態流程：允許的轉換、轉換的前置條件、轉換後的副作用。
- 計算規則：數量、金額、進位與捨去。
- 欄位規則：必填、預設值、唯讀、可見性。
- 錯誤處理：錯誤訊息、阻擋或警告、失敗時資料是否回復。

## 3. 需求層級的權限與限制

依據規定的角色、資料歸屬、狀態或數量限制，是否在**後端**落實，而不只在畫面上隱藏或停用。

候選要寫出：依據的哪一條限制、繞過畫面（直接呼叫 API 或修改傳入值）時會發生什麼。泛用的授權與信任邊界檢查屬於 Risk 軸，本節只看依據明文規定的限制——例如「只有原建立者可以作廢」「已結案的單據不可修改」。

## 4. 範圍外變更

diff 中有依據沒有要求的行為時，**只有造成實際影響才構成候選**：

- 改變了既有流程、既有 API 契約或其他功能的行為。
- 新增了依據沒有要求的對外入口、權限或資料暴露。
- 修改了與本次需求無關的共用程式，影響其他呼叫端。

單純多做、沒有改變既有行為的，不構成候選。

## 5. 測試缺口

本次需求新增或改變的**重要行為**，缺少測試使具體回歸難以被現有測試發現時才構成候選。

候選要寫出：是哪一條需求或驗收條件的行為、哪種具體改動會讓它壞掉卻沒有測試失敗，以及建議補在哪一層（單元、整合或端對端）。這不是覆蓋盤點，只針對本次變更中缺測試會有實際回歸風險的行為。

# mr-review

沿用三軸「找候選 → 主流程查證」，以減少漏查為優先。審查者負責提出有程式碼依據的問題與不確定性，開發者決定是否接受風險；未能證明安全不等於已確認有 bug，也不等於可以排除。

## 模式與必要輸入

資訊已由本輪或對話提供時直接沿用；缺少模式時先詢問，不自行替使用者選擇。

| 模式 | 必要輸入 | 背景來源 | 預設輸出目錄 |
| --- | --- | --- | --- |
| A. 標準 | 目標分支／base ref／commit 範圍，以及變更目的 | 使用者提供的 Issue、文件或說明 | `.ai/code-review/<target>__<current>/` |
| B. Matt Workflow | 目標分支／base ref／commit 範圍 | `.ai/.scratch/<分支對應目錄>/` | 該分支目錄 |

模式 B 讀取實際存在的 `spec.md`、`engineering-spec.md`、`issue-doc.md`、`issue.md` 與本次交付的 `issues/` ticket。engineering-spec 優先於 issue-doc，明確的使用者修正優先於舊文件。文件互相矛盾時記錄差異，不自行選有利於實作的版本。分支目錄對不到、對到多個，或完全沒有背景文件時，請使用者指定；不自行降級模式。

必要輸入缺少時，列出缺項；先不審 diff、不啟動代理、不覆寫報告。使用者若只是詢問或修改本 skill，回答該任務，不啟動模式詢問或 MR 審查。

## 審查邊界與權限

- 預設審查目標分支至 HEAD 的完整 MR 差異，不限最新 commit。目標須由使用者指定。
- 程式碼與測試唯讀；只建立／更新下述兩份本地報告。測試僅在既有授權與環境限制內執行，不建立測試依賴、連線寫入資料庫、故障注入或修改外部系統。無法安全測試時以靜態證據與限制交代。
- 沿變更造成的影響追查未修改的呼叫端、子方法與資源生命週期。未修改的檔案不等於未受影響。
- 純既有且未受影響的問題不冒稱本次回歸；與本次修改的執行路徑直接相關、值得開發者一併處理者，可列「待開發者判斷」，明示既有問題。無關模組不展開全站掃描。
- 比較變更前後行為，不只比較方法簽章。被移除的隱性副作用、context／scope／連線／交易／快取／鎖的更換都是影響範圍的起點。
- 候選記錄與報告不得包含秘密、個資或真實憑證；使用程式位置、欄位名稱與去識別化範例。

## 流程

### 1. 固定快照

解析 target、HEAD，取得 merge-base、commit 清單、變更檔案與完整 diff。分支比較使用三點 diff；明確 commit 範圍則遵循指定範圍。記錄工作區是否有未提交變更，HEAD 審查不自動包含它們；使用者要求審未提交變更時明確記錄實際基準。

目標解析失敗或指定快照無差異時停下說明；未提交變更另行告知，不偷換比較範圍。

**完成條件：**比較起訖、diff、commit 與檔案清單固定，可供三軸使用。

### 2. 建立影響清單

讀取 repo 規範及明確引用的文件，取得背景與技術別。主流程讀 [追查與證據規則](references/trace-and-evidence.md)，並依變更建立：

- 變更的方法／契約與改變的行為，包括移除或縮小的副作用。
- 共用方法的呼叫端清單及前後相鄰操作；必要時一路追至真正的儲存／回應位置。
- 涉及 I/O、資源或交易時，建立例外邊界清單。
- 每項待查位置的責任軸；兩軸重疊由主流程合併，不能因「另一軸負責」而無人追查。

先在審查筆記中記錄，不必把整個 repository 塞進 prompt。共用行為變更的已找到呼叫端須全部有去向；動態呼叫、外部 consumer 或無法確認的 wiring 記為未查明。

**完成條件：**每個變更符號有影響說明與追查去向；高風險呼叫鏈有具體待查節點。

### 3. 三軸平行找候選

| 軸 | 核心責任 | 必讀規則 |
| --- | --- | --- |
| Standards | 正確性、共用行為回歸、API 相容性、實質效能與程式碼品質 | [standards-axis.md](references/standards-axis.md) |
| Risk | 權限、信任邊界、交易／併發、例外與失敗結果 | [risk-axis.md](references/risk-axis.md) |
| Spec | 需求與原有行為、驗收條件、具體測試保護缺口 | [spec-axis.md](references/spec-axis.md) |

使用三個獨立子代理；這是本 skill 授權的審查分工，不授權修改產品或外部系統。代理拿到相同原始事實，各自推理；不把先前代理結論餵給其他軸。不能使用子代理時依序 Risk → Spec → Standards，各自保留結果。

主流程完整讀取三軸規則，再把以下內容完整交給每個代理：
1. 固定快照的指令、refs、merge-base、commit 與變更檔案清單。
2. 本文件的「審查邊界與權限」，以及 trace-and-evidence 全文。
3. 該軸規則全文、repo 規範清單、技術別。
4. 變更目的與背景文件清單（三軸皆提供），影響清單及該軸待查節點。
5. 本次報告位置與唯讀／測試限制。

代理回傳每條候選的：ID、軸／規則依據、位置、前後行為差異、觸發流程、影響、已查保護及位置、未知條件、建議確認程度與 P0–P3。另回傳逐節涵蓋清單與實際呼叫鏈證據，格式見 trace-and-evidence。

**完成條件：**三軸候選與涵蓋證據齊備；「已查無問題」有方法／呼叫端及保護位置。未查明處明列，不能用零候選代替完成。

### 4. 主流程查證與補查漏點

依 trace-and-evidence 的分級方式逐條查證。五項證據是查證維度，不是「任一未知即刪除」的篩選器：
變更關聯、可達性、實際影響、保護是否有效、修正價值。

即使三軸都零候選，主流程仍核對：
- 共用行為清單是否漏了呼叫端或被移除的副作用。
- 成功返回前是否仍有未儲存／未等待／未交付的工作。
- 失敗是否會在業務已提交後改變最終回應；資源初始化與清理是否真的落在 catch 的保護範圍。
- 「不適用／已保護」是否有具體依據，僅因 diff 外、測試通過、有 catch、有 Commit 而排除的是否應重查。
- 新增、放大、暴露與純既有問題是否對照 baseline 分清。

對未查完且可能改變結論的部分繼續補查；受工具、時間或環境限制時記錄審查缺口，不宣稱全數通過。只確認候選正確性而不核對涵蓋面，不算完成。

**完成條件：**每條候選都有「已確認／待開發者判斷／已排除」及理由；影響清單與例外清單無靜默遺漏。

### 5. 寫報告

依 [報告格式](references/report-format.md)：
- `REVIEW.md`：已確認問題、待開發者判斷。兩區明確區分，各條可獨立貼到 MR。
- `REVIEW-COVERAGE.md`：快照、呼叫鏈與例外涵蓋、候選去向、排除依據、未查明處、測試實際結果。

同一路徑重跑時更新兩份報告，包含零問題結果，避免留下舊 findings。只覆寫此技能的指定報告；使用者明確要求保留歷史或指定其他位置時遵從。模式 A 目錄將分支中的 / 改為 -，移除 target 的 origin/。不發送 MR comment，不建立遠端 Issue。

最終回覆：模式與快照、三軸候選數及各去向、合併數、是否平行、已確認與待判斷數／最高嚴重度、未查明項數、測試結果與報告連結。零 finding 且有缺口時，寫「目前未確認問題，但有 N 項未完成查核」，不寫成完整審查通過。

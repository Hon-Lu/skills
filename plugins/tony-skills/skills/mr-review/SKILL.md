# mr-review

合併前的最後一關。流程分兩段，角色刻意分開：

- **找**：Standards、Risk、Spec 三軸各由獨立子代理平行審查，各自產出**候選**。
- **驗**：主流程逐條重新查證候選，通過證據門檻的才成為 **finding**，寫進 `REVIEW.md`。

子代理負責涵蓋面，主流程負責把關。候選不等於 finding，子代理的報告也不是輸出。

## 兩種模式

開場第一件事是**主動詢問使用者要走哪一種**，等使用者回答後才繼續。兩種模式擇一，由使用者決定。

| | **A. 標準** | **B. Matt Workflow** |
| --- | --- | --- |
| 適用 | 一般 MR、PR、分支或 commit 範圍審查 | 專案採 Matt workflow，`.ai/.scratch/` 下有本分支的目錄 |
| 使用者要提供 | 目標分支 **+ 變更目的** | **只有目標分支** |
| 審查背景來源 | 使用者提供的 Issue、文件或口頭說明 | `.ai/.scratch/<分支名>/` 下的規格與 ticket |
| 輸出位置 | `.ai/code-review/<target>__<current>/REVIEW.md` | `.ai/.scratch/<分支名>/REVIEW.md` |

## 必要輸入

### 共通

**目標分支、base ref 或 commit 範圍**，由使用者明確指定——`main` 不一定是這條 branch 的分歧點。

### A. 標準

另外要**本次變更的目的**。Issue、需求、開發文件或驗收條件皆可；沒有額外文件時，由使用者口頭說明變更目的。

審查背景的範圍就是使用者給的內容：指定的文件一律讀取，缺的部分請使用者補齊，而不是自行到 repository 搜尋可能相關的規格或 ticket。

### B. Matt Workflow

審查背景由 `.ai/.scratch/<分支名>/` 取得，讀取該目錄下實際存在的：

1. `spec.md` —— 需求、範圍與行為基準。
2. `engineering-spec.md` 或 `issue-doc.md` —— 看這個 feature 實際用哪一份；兩份都在時以 `engineering-spec.md` 為主。
3. `issues/` 底下的 ticket —— 本次變更實際交付了哪幾張票、各自的驗收條件。

分支名對不到目錄、對到多個目錄，或目錄存在但上述文件都沒有時，**停下來問使用者**：指定正確的目錄，或改走模式 A。模式由使用者決定，不自行降級——降級的代價是使用者被要求重打一份現成文件裡就有的背景。

### 缺輸入時

停止並列出缺少的項目請使用者補充，**此時不讀 diff、不審程式碼、不建立 `REVIEW.md`**。沒有變更目的就開審，等於拿實作反推需求，會把「照需求做的」報成 finding。

## 流程

### 1. 固定審查範圍

1. `git rev-parse <target>` 確認目標可解析。
2. 以 `git merge-base <target> HEAD` 取得分歧點，記下 `git diff <target>...HEAD`（三點，對 merge-base 比較）與 `git log <target>..HEAD --oneline`。
3. 確認 diff 非空，並列出變更檔案。

目標解析失敗或 diff 為空時在這一步停下回報，不啟動子代理。

**完成條件**：取得可解析的 merge-base、非空 diff、commit 清單與變更檔案清單。

### 2. 收集各軸依據

- **Spec 依據**：依模式取得的審查背景（模式 A 為使用者提供的內容，模式 B 為 `.ai/.scratch/<分支名>/` 下的文件）。
- **repo 規範**：repository 中實際存在、記載程式碼寫法或架構機制的文件，例如 `CLAUDE.md`、`AGENTS.md`、`CONTEXT.md`、`CODING_STANDARDS.md`、`CONTRIBUTING.md`，以及這些文件以 `@` 匯入或明確指向的規範文件。只列出實際存在的檔案，不另外推測。Standards 與 Risk 兩軸共用。
- **技術別**：由變更檔案判斷專案技術，決定 Standards 與 Risk 軸的技術別補充要套用哪一個子節。

**完成條件**：三軸各自有一份可交給子代理的依據清單。

### 3. 平行啟動三軸子代理

| 軸 | 回答的問題 | 規則 |
| --- | --- | --- |
| **Standards** | 寫法是否達到工程基準？ | `references/standards-axis.md` |
| **Risk** | 是否讓人做不該做的事，或讓資料在失敗與同時操作下不一致？ | `references/risk-axis.md` |
| **Spec** | 是否正確、完整地實現需求？ | `references/spec-axis.md` |

三軸以**平行子代理**執行，彼此不共用 context，避免一軸的判斷遮蔽另一軸：寫法合規卻做錯需求、照需求做卻引入越權或超扣、邏輯正確卻在同時操作下資料錯亂，每一種都要有一軸專門負責抓到。Risk 軸獨立出來，是因為它的問題幾乎都要從入口追到資料寫入才能判斷，需要一份不被其他面向分散的 context。

每個子代理拿不到本 skill 的任何檔案，**所需內容一律完整貼入 prompt**：

| 內容 | Standards | Risk | Spec |
| --- | --- | --- | --- |
| diff 指令、merge-base、commit 清單、變更檔案清單 | ✓ | ✓ | ✓ |
| 該軸規則檔全文 | ✓ | ✓ | ✓ |
| repo 規範檔案清單與技術別 | ✓ | ✓ | |
| Spec 依據（文件路徑或內容、使用者說明的變更目的） | | | ✓ |
| 本文件的「審查範圍」「追查要求」「明確排除」「候選格式」四節全文 | ✓ | ✓ | ✓ |

執行環境無法啟動子代理時，改為在主流程**依序**執行三軸（Risk → Spec → Standards）：每完整做完一軸並寫下其候選與涵蓋清單，才開始下一軸，各軸候選分開記錄到第 4 步才合併。

**完成條件**：三軸都回傳了候選清單與涵蓋清單。涵蓋清單缺少 diff 實際涉及的面向時，要求該子代理補齊，或由主流程補查該面向。

### 4. 逐條驗證候選

對三軸的每一條候選，主流程**親自回到程式碼重新查證**，依序走完「證據門檻」五關。子代理的自評只是線索：尤其第 4 關「未被保護」，要自行搜尋其他呼叫端、上游驗證、交易範圍、資料庫約束與既有測試。

- 任一關不成立 → 刷掉，不寫出。
- 多軸指向同一根因（例如 Spec 軸的「需求限制未在後端落實」與 Risk 軸的「缺少擁有權驗證」）→ 合併成一條 finding，保留各軸證據中較具體的部分。
- 驗證過程中另外發現的問題，同樣走完五關才可寫出。
- 通過者判定「確認程度」與「嚴重程度」；各軸規則表的嚴重度是預設值，最終以「嚴重程度」一節的定義為準。

**完成條件**：每一條候選都有「成立」或「刷掉」的結論，成立者都有確認程度、嚴重程度與變更檔案行號。

### 5. 輸出

依「輸出」一節寫入 `REVIEW.md` 並回覆使用者。

## 審查範圍

1. 審查目前分支相對於目標分支的完整 MR diff，不限於最新 commit。
2. 參考相關 Issue、需求、開發文件及驗收條件，但不擴大變更範圍。
3. 為確認實際影響，可追查必要的呼叫端、被呼叫端、模型、資料庫存取、權限與測試。
4. 只有符合下列任一條件時，才可回報 diff 外的程式碼問題：
   - 本次變更新增了到該問題的可達路徑。
   - 本次變更使既有問題更容易觸發或影響明顯擴大。
   - 本次變更依賴該既有行為，導致本次需求無法正確成立。
5. 追查過程中看到、但不符合第 4 點的既有問題，不列入候選。

## 追查要求

沿資料流與呼叫關係追查，而不只是逐行閱讀 diff：每條候選都要確認問題是否已在呼叫端、上游驗證、交易、資料庫約束或框架機制中被處理。**只套用 diff 實際涵蓋的面向**，不因為規則列了某一節就到 diff 以外找問題。

## 明確排除

下列內容不構成候選：

- 未受本次變更影響的既有問題。
- 純排版、個人偏好或與本次變更無關的重構建議。
- 奈秒級、常數級或無可觀測影響的微型效能最佳化。
- 沒有資料量、呼叫頻率或 I/O 證據支撐的效能猜測。
- 只有理論可能、但無合理觸發路徑的 Null、並行、資安或例外風險。
- 已由框架、型別系統、資料庫約束、上游驗證或現有保護機制可靠處理的情況。
- 為了填滿檢核清單而產生的評論。
- 無法指出實際錯誤結果的「可能有問題」「建議確認」「最好改成」類評論。

## 候選格式

子代理回傳兩部分。

**候選清單**，每條：

```markdown
### <簡短且具體的問題標題>

- 軸：Standards / Risk / Spec
- 依據：<該軸規則檔的節次；repo 規範檔與條文；或引用的 spec／ticket 原文>
- 位置：`相對路徑:行號或行號範圍`
- 觸發情境：<什麼輸入、狀態或操作流程會觸發>
- 實際影響：<錯誤結果、資料異常、越權、效能退化或需求不符>
- 已查過的保護：<查了哪些呼叫端、驗證、交易、約束或測試，為何沒有擋住>
- 建議嚴重度：P0–P3
```

**涵蓋清單**：該軸規則的每一節一行，標明「適用，候選 N 條」「適用，已查無問題」或「不適用（原因）」。

## Finding 證據門檻

提出 finding 前，依序確認：

1. **變更關聯**：問題由本次 diff 引入、改變或明顯放大。
2. **可達性**：存在合理輸入、狀態或操作流程可以觸發。
3. **實際影響**：可說明錯誤結果、資料異常、越權、明顯效能退化或需求不符。
4. **未被保護**：確認其他呼叫端、驗證、交易、限制或測試沒有已經處理。
5. **修正價值**：本次合併前處理具有實際價值，不只是理論上的完善。

五關全數成立才可輸出。**任何來源的候選都逐條走完五關**——任一軸報出的、主流程驗證時另外發現的，一律不因來源而免驗。

## 確認程度

- `已確認問題`：可由程式碼、執行結果或明確需求直接證明。
- `待確認風險`：已有具體程式碼路徑與實際影響，只差一項可明確驗證的環境、資料、設定或需求條件。

`待確認風險` 必須同時寫明：

- 已確認的程式碼事實。
- 唯一待確認的條件。
- 該條件成立時的具體影響。
- 可如何快速驗證。

若缺少多項前提、只能依賴猜測，或驗證後很可能不構成問題，不得列為 `待確認風險`。

## 嚴重程度

- `P0`：重大服務、資料或資安事故，必須阻擋。
- `P1`：一般情境可觸發的嚴重錯誤、越權或核心流程失效，應阻擋。
- `P2`：特定合理情境下的功能、回歸、實質效能、並行或維護問題，合併前應處理或確認。
- `P3`：影響較低，但與本次變更直接相關、證據明確、修正成本合理且有實際品質價值的小問題。

P3 可保留有價值的小細節，但仍必須符合完整證據門檻。不得把微型最佳化或不確定猜測包裝成 P3。

## 輸出

有 findings 時，依模式決定寫入位置：

| 模式 | 路徑 |
| --- | --- |
| A. 標準 | `.ai/code-review/<target-branch>__<current-branch>/REVIEW.md` |
| B. Matt Workflow | `.ai/.scratch/<分支名>/REVIEW.md`（與 `issues/` 同層） |

模式 A 的目錄名先正規化：移除目標分支的 `origin/`，並將目標及目前分支名稱中的 `/` 改為 `-`。

使用者明確指定其他輸出位置時依其指定，不自行改寫到別處。

既有檔案直接覆寫——本 skill 可對同一條 branch 重複執行，每次都反映當下狀態，不保留上一輪的內容當歷程。

findings 依 `P0` 至 `P3` 排序，使用以下格式：

```markdown
## [P0-P3] 簡短且具體的問題標題

* 問題類型：<類型>
* 確認程度：已確認問題 / 待確認風險
* 影響範圍：`相對路徑:行號或行號範圍`
* 問題說明：<觸發情境、目前行為、預期行為、現有保護為何無法避免，以及實際影響>
* 建議修正方向：<聚焦的修正方向；若為待確認風險，包含快速驗證方式>
```

每個 finding 必須指出變更檔案與行號。未實際執行測試時，不得宣稱測試通過。

`REVIEW.md` 只放可獨立貼至 MR comment 的 findings，不加入稱讚、審查過程、各軸的候選清單或涵蓋清單、未變更內容摘要、被刷掉的候選或「未確認但可留意」清單。

沒有 findings 時不要建立檔案，回覆：`未發現 Code Review Finding。`

最終回覆同時列出：

- 本次採用的模式、目標分支、merge-base 與 commit 數。
- 三軸各自的候選數與通過門檻數（例如 `Standards 7 → 2、Risk 4 → 1、Spec 3 → 1`），跨軸合併的條數，以及三軸是否以子代理執行。
- findings 數量與最高等級。
- 實際測試結果，或註明未執行測試。
- 有建立時的 `REVIEW.md` 路徑。

## 執行限制

- **只建立或覆寫 `REVIEW.md`**，程式碼、測試與設計文件一律唯讀。發現問題一律回報，修不修由使用者決定。
- 本 skill 自成一套審查流程：不遞迴調用本 skill，也不調用其他 code review skill 取代三軸。
- 讀文件是為了取得審查背景；測試覆蓋盤點是另一件事，本 skill 不做。

## 下一步引導（純提示，不主動調用）

- **有 P0 / P1** → 提示先處理再合併；修正屬於實作，本 skill 不動程式。
- **只有 P2 / P3** → 提示由使用者決定本次處理或另開 ticket。
- **修正後** → 提示重跑本 skill，`REVIEW.md` 會覆寫成當下狀態。
- **全部通過** → 本 skill 到此結束，不主動接續任何後續流程。模式 B 若專案另有既定的後續步驟，由使用者自行決定。
